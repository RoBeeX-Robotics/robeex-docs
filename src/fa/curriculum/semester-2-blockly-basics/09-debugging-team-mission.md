# جلسه ۹: اشکال‌زدایی با فرضیه و شاهد

اشکال‌زدایی یعنی فرق میان «انتظار» و «مشاهده» را دقیق بنویسیم، یک علت محتمل انتخاب کنیم، فقط یک تغییر بدهیم و نتیجه را ثبت کنیم. تغییر هم‌زمان چند بلوک شاید اتفاقی جواب بدهد، اما چیزی یاد نمی‌دهد.

## در پایان این جلسه می‌توانید

- خطای ساختاری، منطقی، پارامتری و اجرایی را جدا کنید؛
- قبل از اصلاح، نسخه خراب را حفظ کنید؛
- مسیر اجرای پشته را از Start تا پایان ردیابی کنید؛
- یک فرضیه قابل آزمون و یک تغییر کمینه بنویسید؛
- توضیح دهید نتیجه چه شاهدی برای رد یا تأیید فرضیه بود.

::: teacher آماده‌سازی پیش از کلاس
برای هر گروه یک نسخه کپی با یکی از خطاهای بی‌خطر آماده کنید: بلوک آویزان، Wait در جای اشتباه، شمارنده حلقه 3 به‌جای 4، شاخه else خالی یا ترتیب رنگ نادرست. پارامتر پروازی خطرناک فقط برای تحلیل آفلاین نشان داده شود و پیش از هر اتصال حذف شود.
:::

## ۱. «کار نکرد» یک مشاهده کافی نیست

جمله ضعیف: «مربع خراب شد.»

جمله قابل استفاده: «بعد از ضلع دوم، برنامه Land را اجرا کرد؛ انتظار داشتیم دو ضلع دیگر باقی بماند.»

یک گزارش خوب سه جزء دارد: مرحله دقیق، رفتار دیده‌شده و رفتار مورد انتظار.

::: teacher تمرین بازنویسی
جمله‌های «LED عجیب بود»، «پرنده بد رفت» و «Run نمی‌شود» را بدهید. گروه باید آن‌ها را با شاهد قابل مشاهده بازنویسی کند؛ مثلاً «Run خاکستری است و یک بلوک جدا کنار پشته دیده می‌شود».
:::

## ۲. چهار خانواده خطا

| نوع خطا | نمونه | اولین بررسی |
| --- | --- | --- |
| ساختاری | بلوک آویزان یا اتصال ناسازگار | مسیر پشته و شکل اتصال |
| منطقی | ترتیب غلط، Land داخل حلقه، else خالی | خواندن جمله‌به‌جمله |
| پارامتری | واحد یا مقدار نامناسب، شمارنده اشتباه | عدد، واحد و محدوده |
| اجرایی/سامانه | اتصال قطع، حسگر نامعتبر، باتری کم | وضعیت دستگاه و تله‌متری |

::: teacher نکته مربی — مشکل را زود «کد» ننامید
اگر برنامه درست است ولی دستگاه Disconnected است، جابه‌جایی بلوک‌ها کمکی نمی‌کند. هنرجو باید لایه نرم‌افزار و وضعیت فیزیکی را جدا بررسی کند.
:::

## ۳. اول نسخه خراب را نگه دارید

1. برنامه را Duplicate و نام را با `-debug-01` ذخیره کنید.
2. از برنامه اصلی عکس یا یادداشت ساختار بگیرید.
3. نتیجه مورد انتظار را از روی هدف مأموریت بنویسید.
4. نتیجه دیده‌شده را بدون تفسیر ثبت کنید.
5. فقط روی نسخه Debug تغییر دهید.

::: teacher چرا نسخه خراب ارزش دارد؟
بدون نسخه اولیه نمی‌توان فهمید کدام تغییر مشکل را حل کرد و شاید اصلاح جدید خطای دیگری بسازد. حفظ شواهد بخشی از روش مهندسی است، نه شلوغ‌کردن فایل‌ها.
:::

## ۴. ساختار را با انگشت ردیابی کنید

  <img src="/assets/curriculum/semester-2/blockly-disconnected-dangling-block.webp" alt="بلوک آویزان که به مسیر اجرای اصلی Blockly متصل نیست" width="809" height="443" loading="eager" decoding="async">
  <figcaption>از Start تا آخر پشته خط بکشید. بلوکی که روی این مسیر نیست، خودکار اجرا نمی‌شود.</figcaption>
</figure>

1. Start را پیدا کنید.
2. اتصال هر بلوک به بعدی را دنبال کنید.
3. داخل حلقه و هر دو شاخه شرط را جدا بخوانید.
4. پشته دوم یا بلوک آویزان را علامت بزنید.
5. Land و محل آن را پیدا کنید.

::: teacher نکته مربی — جواب را نشان ندهید
اگر بلوک آویزان واضح است، فقط بپرسید «مسیر اجرا از Start به این بلوک می‌رسد؟» هنرجو باید با ردیابی پاسخ را کشف کند.
:::

</figure>

::: teacher مرز ابزار
Undo شاهد را جایگزین نمی‌کند. قبل از Undo بنویسید چه تغییری داده شد و چرا برگشتیم. Clean up فقط چیدمان دیداری را مرتب می‌کند و منطق برنامه را اصلاح نمی‌کند.
:::

## ۶. جدول فرضیه

| انتظار | مشاهده | فرضیه | فقط یک تغییر | نتیجه | فرضیه تأیید شد؟ |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

نمونه: انتظار ۴ چشمک، مشاهده ۳ چشمک، فرضیه «شمارنده حلقه 3 است»، تغییر «فقط شمارنده به 4»، نتیجه «۴ چشمک»، فرضیه تأیید شد.

::: teacher نکته مربی — فرضیه باید ردشدنی باشد
«برنامه خراب است» فرضیه نیست. «بلوک قرمز به پشته متصل نیست» قابل بررسی است. از گروه بپرسید چه نتیجه‌ای نشان می‌دهد فرضیه‌شان غلط بوده است.
:::

## مأموریت تیمی: برنامه ناشناس

1. نقش‌ها را تقسیم کنید: خواننده کد، بازبین ایمنی، ثبت‌کننده فرضیه.
2. هدف برنامه را از کارت مأموریت بخوانید.
3. بدون Run، ساختار و منطق را ردیابی کنید.
4. هر خطر احتمالی را قبل از اتصال حذف کنید.
5. یک فرضیه اولویت‌دار بنویسید.
6. فقط یک تغییر روی نسخه Debug بدهید.
7. اگر برنامه LED/زمینی است، پس از تأیید اجرا کنید.
8. اگر حرکت دارد، ابتدا مرور خشک و چک‌لیست کامل انجام دهید؛ اجرای واقعی اختیاری و با اجازه مربی است.
9. نتیجه را در جدول فرضیه ثبت کنید.
10. اگر فرضیه رد شد، از داده تازه برای فرضیه بعد استفاده کنید.

<div class="lesson-checkpoint">
<strong>توقف و بررسی:</strong> هیچ خطای خطرناک برای «دیدن نتیجه» اجرا نمی‌شود. پارامتر خارج مرز، Land گمشده یا حلقه بی‌پایان باید در حالت آفلاین پیدا و اصلاح شود.
</div>

::: teacher خطاهای پیشنهادی بر اساس سطح
- پایه: بلوک آویزان یا ترتیب رنگ؛
- متوسط: Wait داخل جای اشتباه یا شاخه else خالی؛
- پیشرفته: شمارنده مربع 3 یا Land داخل حلقه.

به هر گروه فقط یک خطای اصلی بدهید تا روش یک‌متغیره قابل سنجش بماند.
:::

## ارائه ۹۰ ثانیه‌ای گروه

گروه باید بدون نمایش جزئیات اضافی بگوید:

1. انتظار چه بود؟
2. چه شاهدی دیدیم؟
3. فرضیه چه بود؟
4. دقیقاً چه چیز را عوض کردیم؟
5. نتیجه فرضیه را تأیید کرد یا رد؟

::: danger
اشکال‌زدایی اجازه اجرای برنامه ناایمن نیست. اگر علت نامعلوم است، برنامه کوتاه‌تر و بخش‌های غیرپروازی جدا آزمایش می‌شوند. ورود به پرواز فقط بعد از بازبینی کامل انجام می‌شود.
:::

## کوییز نهایی

مراحل زیر را مرتب کنید: تغییر یک بلوک، نوشتن مشاهده، Run دوباره، نوشتن انتظار، ساخت فرضیه. سپس توضیح دهید چرا پاک‌کردن کل برنامه روش اول نیست.

::: teacher پاسخ و معیار
انتظار → مشاهده → فرضیه → تغییر واحد → آزمون/Run. پاک‌کردن کل برنامه رابطه علت و نتیجه و شواهد را از بین می‌برد. معیار عملکردی، یک جدول کامل با اصلاح کمینه و دفاع شاهد‌محور است.
:::
